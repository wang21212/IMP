# IMP Reflect — 自迭代评估回路

## 作用

IMP 的自迭代闭环：汇聚本机所有项目的 trace 事件，识别模式，产出评估报告和候选改进项，写入 IMP 仓库 intent-log 等用户拍板迭代 IMP 自身。

## 触发条件

用户说「评估 IMP」「imp-reflect」「回看 IMP」「迭代 IMP」时触发。不自动触发，不主动打扰。

## 前置：定位 IMP 源仓库

通过以下顺序定位 IMP 源仓库（IMP_HOME）：
1. 环境变量 `IMP_HOME`
2. 默认路径 `C:\Users\WangShuXuan\CascadeProjects\IMP`
3. 若都不存在，向用户询问 IMP 仓库路径

## 流程

### Phase 1: 加载项目注册表 + 自动发现补登记

1. 读 `<IMP_HOME>/.imp/projects-registry.md`
2. 若注册表不存在或为空 → 运行 `scripts/discover-projects.ps1` 扫描本机常见工作目录，找出所有含 `.imp/memory/` 的项目，自动补登记
3. 若注册表已有项目但最近活跃时间超过 30 天 → 也可重新跑 discover 补充新项目（可选）

### Phase 2: 汇聚各项目 trace

逐项目读 `<项目路径>/.imp/trace/events.ndjson`：
- 文件不存在 → 跳过（该项目可能 onboard 后还没跑过 IMP 流程）
- 解析失败 → 记录异常，跳过该文件，不阻塞整体评估
- 全部读入内存，合并成一个事件列表

**包含 IMP 仓库自身的 trace**：IMP 仓库自身也是注册表中的一个项目，迭代 IMP 时产生的事件也会被评估（自举）。

### Phase 3: 聚合分析

按以下维度聚合事件，识别模式：

#### 3.1 Skill 失败率
按 skill 分组，统计 `verify_result` 事件的 pass/fail 比例。
- 失败率 > 30% 的 skill → 标记为「规则可能有歧义或验证标准不清」

#### 3.2 升级路由频次
统计 `route_upgrade` 事件，按 from_level → to_level 分组。
- 频繁出现「任务级→骨架级」→ 说明级别判定标准对骨架级触发条件描述不够清晰
- 频繁出现「功能级→骨架级」→ 说明功能级和骨架级的边界判定有盲区

#### 3.3 反复纠偏
统计 `correction` 事件，按 detail 关键词聚类。
- 同类纠偏反复出现（如多次「扩大范围」「改了不该改的」）→ 说明任务拆解或皮骨检查环节有系统性问题

#### 3.4 意图反复锁定
统计 `intent_locked` 事件，看同一项目短时间内是否有多次锁定且摘要互相矛盾。
- 矛盾锁定多 → 说明 imp-intent 的细化阶段不够充分，或完备度评估太宽松

#### 3.5 平台分布
按 agent 字段统计各平台使用频次。
- 某平台失败率显著高于其他 → 说明该平台适配壳有问题

### Phase 4: 产出评估报告

在 `<IMP_HOME>/.imp/evaluations/YYYY-MM-DD-eval.md` 写报告：

```markdown
# IMP 评估报告 — {YYYY-MM-DD}

## 评估范围
- 扫描项目数：{N}
- trace 事件总数：{N}
- 时间跨度：{最早事件} ~ {最晚事件}
- 平台分布：{windsurf: N, dsh: N, ...}

## 关键发现

### 1. {发现标题}
- 证据：{引用具体 trace 事件，含项目名/时间/skill}
- 模式：{描述反复出现的模式}
- 可能原因：{推断}
- 候选改进项：{一句话描述可能的改进方向}

### 2. {发现标题}
...

## 候选改进项汇总

| # | 改进项 | 证据强度 | 建议级别 | 来源发现 |
|---|--------|----------|----------|----------|
| 1 | {一句话} | 高/中/低 | 功能级/骨架级 | 发现 #N |
| 2 | {一句话} | 高/中/低 | 功能级/骨架级 | 发现 #N |

## 未发现问题的方面
- {列出表现正常的维度，避免只看负面}
```

**证据强度判定**：
- 高：同一模式在 3+ 项目或 5+ 事件中出现
- 中：同一模式在 2 个项目或 3-4 事件中出现
- 低：单次出现，但有明确改进价值

### Phase 5: 候选改进项写入 intent-log

把评估报告中的候选改进项追加到 `<IMP_HOME>/.imp/memory/intent-log.md`，格式：

```
## [待评估] {YYYY-MM-DD} — 来自 imp-reflect 评估
- [ ] {候选改进项1}（证据强度：高，建议级别：功能级）
- [ ] {候选改进项2}（证据强度：中，建议级别：骨架级）
...
```

### Phase 6: 人确认（强制暂停）

向用户展示评估报告摘要 + 候选改进项列表，问：
「要迭代哪些？选一个开始 → 走 imp-intent 锁定意图」

等用户选择。不自动开始迭代。

### Phase 7: 写入 trace 事件

向 IMP 仓库自身 `.imp/trace/events.ndjson` 追加一条 `verify_result` 事件（imp-reflect 自身也留痕）：
- outcome: pass（评估报告产出成功）/ fail（出错）
- detail: 评估了 N 个项目，产出 M 个候选改进项

## 评估边界

- **只看模式，不看个案**：单次失败不构成改进依据，需识别反复出现的模式
- **只建议，不执行**：imp-reflect 产出候选改进项，不直接改 IMP 代码
- **证据优先**：每个候选改进项必须引用具体 trace 事件作为证据
- **闭环靠人**：用户拍板后才走 imp-intent → imp-architect/imp-feature 迭代
